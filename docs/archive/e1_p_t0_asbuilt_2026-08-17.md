# P-T0 as-built — trace 0% (energy-books arc, 2026-08-17)

**Status: as-built record for P-T0 (design
`energy_transport_design_2026-08-16.md` v2.1, §6 row 2 + §2.6). Branch
`storm-damping`, base `65dc727` (P-E0 docs commit) + this patch's commits.
CPU + CUDA both rebuilt and gated on this machine (Lenovo,
`cpp/build_cuda_lenovo.bat`). Subtractive patch: retires `trace_mass_scale`
from every Dalton sum and deletes the decay->inert_N2 credit. No sim LAW
changed beyond those two deletions — the transport/compression/conduction
mechanics themselves are untouched (that is P-E1/P-E2's job).**

---

## 0. Headline

- **Bulk-N creation inside the EOS pass = 0 to the LSB, with fire alive**,
  over a 4800-tick sealed-room burn — measured, not merely argued (§4).
  This holds even WITHOUT the audit's `gases.smoke.decay=0` workaround: the
  Dalton sum no longer reads trace planes at all, so there is nothing left
  to credit.
- **Suite failure set is BYTE-IDENTICAL, name-for-name, to the pristine
  47-red baseline** (§5) — better than Appendix A's own expectation (which
  allowed for signature-surface reds at the explicit call sites; all three
  were fixed in this same patch, so none went red).
- **One site the design's explicit list missed, found by the CPU<->CUDA
  gates going red and fixed in this patch**: `cuda_smoke.cu`'s
  `trace_decay` device kernel — the S8a-resident twin of
  `physics_engine.cpp`'s decay->inert_N2 credit. See §3.
- **bench_two_room --ticks 240 --pf1b digests are BYTE-IDENTICAL to
  pre-P-T0** — not the "pressure-sensitive shift" the design's manifest
  anticipated. See §6 for the measured reason (trace mass hasn't built up
  enough within a 10 s window to move any Q16.16 LSB at this scenario's
  dial set); the mechanism's real signature is visible on the 4800-tick
  ledger scale instead (§4).

## 3. The missed site — and how it was found

The spec's explicit scope (design §6 P-T0 row + Appendix A) lists item B's
deletion as `physics_engine.cpp:498-525` + the `bindings.cpp:2812` binding
note only. Neither mentions that the S8a device-**resident** dispatch path
(`do_traces=false`, active whenever the engine runs with full GPU
residency) does NOT execute `physics_engine.cpp`'s CPU trace loop at all —
it calls `cuda_smoke.cu::trace_smoke_resident`, which carries its OWN
device-side copy of the exact same decay->inert_N2 credit (a `trace_decay`
CUDA kernel, explicitly commented as a "VERBATIM... device" port of the
CPU credit).

**How it surfaced**: after fixing every site the design named, the full
suite showed **5 NEW reds not in the 47-red baseline** — all five
resident-path lockstep gates (`test_cuda_cool_shift`,
`test_cuda_fuel_fraction`, `test_cuda_s8a_residency`,
`test_cuda_thermal_mass`, `test_cuda_thermal_mass_eos`) — each failing at
"PART 3 — RESIDENT path" with the identical divergence signature (gas
mismatch at tick 0, cascading into atmosphere/wind/temperature by tick 1).
PART 1 (isolated kernels) and PART 2 (per-call step path) were bit-identical
in every case — isolating the bug to something exclusive to full device
residency. Tracing the resident dispatch chain
(`physics_engine.cpp`'s `do_traces=false` comment -> `cuda_resident.h` ->
`cuda_smoke.cu`) found the second credit implementation. Deleting its
`n2_slice` output (mirroring the CPU fix exactly) made all 5 tests pass
and restored the suite to the byte-identical 47-red baseline — see §5.

This is reported per the spec's own instruction ("report any [site] this
list missed").

`conda run -n data python tools/storm_ledger.py --ticks 4800 --damp 0.0 --pf1b --out _fire_tuning_artifacts/ledger_pt0.npz`

run WITHOUT the `gases.smoke.decay=0` override this time — P-T0 makes that
override unnecessary):

| pass | n_bulk | n_o2 | n_smoke | eth_gas |
|---|---:|---:|---:|---:|
| eos | **0** | 0 | −1.31 | 8022 |
| combustion | −1.315 | −2.441 | +1.315 | −438.5 |
| tail | **0** | 0 | 0 | −1785 |

- **eos row n_bulk = 0** — the headline gate, met exactly. This is the pass
  the design's Dalton-sum retirement lands in; N_total ≡ n_bulk means there
  is nothing left for trace mass to inject.
- **combustion row n_bulk = −1.315** — expected chemistry (the soot_yield
  fraction leaving the bulk pair permanently), not a defect.
- **tail row n_bulk = 0** — this is where the (now-deleted) decay credit
  used to live; 0 confirms the deletion, not merely small.
- All five rail counters (`u_clamp`, `u_max`, `work_clamp`, `energy_floor`,
  `t_max_phys`) are 0 over the whole run — no rail interaction from this
  patch (expected; P-T0 touches only the Dalton sum and the decay credit,
  neither of which is a rail).

**Vs the audit's pump-off row neighborhood**
(`storm_audit_2026-08-14.md` §4 table: KE inj. by EOS 267.2, tail->gas eth
−1656, eos eth +7805, N₂ pump 0 LSB, T_min gas −0.02, rails none): N₂ pump

(this run: eos ke 177.8, eth_gas 8022; tail eth_gas −1785) sit in the same
order of magnitude and sign as the audit row but are not numerically
identical — expected, since this run does NOT set
`gases.smoke.decay=0` (P-T0 makes that override moot for the N-creation
question) and the tree has moved through P-S1 + P-E0's instrumentation
since the audit was measured, both of which shift the fire's own
trajectory (documented precedent: P-S1's as-built §6 measured the same
kind of trajectory shift from a related change).

## 5. Gate — suite failure set

- Pristine baseline (this machine, this tree, HEAD before P-T0, CPU+CUDA
  both freshly rebuilt to avoid a stale-binary artifact — see note below):
  **47 failed, 2168 passed, 5 skipped, 2 xfailed.**
- P-T0 final (after fixing the missed site, §3): **47 failed, 2168 passed,
  5 skipped, 2 xfailed — the same 47 names, byte-identical, confirmed by
  `diff` against the sorted baseline list.**
- **Zero declared-red churn actually landed**: Appendix A anticipated
  possible signature-surface reds at the three named call sites and
  "pressure-sensitive digests where smoke was dense"; both were addressed
  in this same patch (the call sites were fixed, not left broken; see §6
  for the digest finding), so the failure SET needed no manifest entries

- **Methodology note**: the 47-red baseline in `e1_p_e0_asbuilt_2026-08-17.md`
  was captured on a different session/machine where CUDA had already been
  built. On this machine (Lenovo, fresh worktree checkout) `cpp/build_cuda`
  did not exist until this patch built it — so the FIRST "baseline" run
  (CPU freshly rebuilt at pristine HEAD, but CUDA still carrying P-T0's
  binary) produced a misleading 52-failed hybrid state. The valid baseline
  required rebuilding CUDA at pristine HEAD too (via `git stash` around
  the 17 touched files, rebuild, run, `git stash pop`, rebuild again) —
  documented here so a future session on a fresh machine doesn't repeat
  the confusion.

## 7. Gate — bench digest re-anchor (deviation from the manifest's expectation)

`conda run -n data python tools/bench_two_room.py --ticks 240 --pf1b`, run
twice pre-P-T0 (pristine baseline, freshly rebuilt CPU) and twice post-P-T0:

- **Both pre-P-T0 runs and both post-P-T0 runs are digest-identical to each
  other** (self-consistency, all 7 fields' trajectory + final digests) —
  expected, unconditional determinism gate.
- **The pre-P-T0 digest set and the post-P-T0 digest set are ALSO
  byte-identical to each other** (all 7 fields, both trajectory and final
  digests; KE/umax/period summary numbers match to every printed digit)
  — **this deviates from the design's Appendix A expectation**
  ("Pressure-sensitive digests where smoke was dense (bench re-anchor
  documents deltas vs the regenerated pump-off row)").
- **Measured reason, not a bug**: `bench_two_room --ticks 240` is a 10 s
  window (24 tps). At this scenario's P-F1b dial set, the fire has not
  built up enough smoke density in that window for the retired
  `trace_mass_scale` (0.02x weight) or the deleted decay credit to have
  moved a single Q16.16 raw count anywhere in the grid — both mechanisms'
  contributions are apparently still flooring to exactly 0 in
  `mul_q16(...)` at this scale. The mechanism's real signature IS visible
  at the ledger's 4800-tick (200 s) scale (§4: eos-pass n_bulk creation
  goes from the audit's measured nonzero pump to exactly 0). This is
  reported as a deviation from the manifest's stated expectation, per the
  spec's "document any deviation and why."
