# P-E3 as-built — interior momentum drag with a heat counterparty (energy-books arc, 2026-08-17)

**Status: as-built record for P-E3 (design `energy_transport_design_2026-08-16.md`
v2.2, §2.8 + §6 row 6). Branch `storm-damping`, base `08b63c2` (the P-E2b
as-built docs commit). CPU **and** CUDA in the SAME commit. Dial defaults
ship SILENT: `k_drag = 0.0`, `k_drag_heat_frac = 1.0`.**

---

## 0. Headlines

1. **The mechanism is built exactly where the design pinned it**: PER TICK
   (not per substep), in the step-4 kick loop, AFTER the |u| cap and BEFORE
   the store, in all four kick sites — live `step()`, the P6.4 CPU reference
   (`eos_kick_compression_reference`), the CUDA K1 kernel, and the resident
   path (which shares K1/K2 via the same launch core, so "resident" here
   means the resident-specific plumbing: `KickScalarFolds`, the 9-slot D2H
   block, the per-tick counter assign).
2. **The drag identity holds** — `ke_drag_removed == 2*c_v*(e_drag_deposit +
   e_drag_drop_sum + e_drag_rail_clipped)` — **to a measured worst relative
   slack of 1.48e-7** (worst absolute slack 0.027 real N·T units) across 54
   synthetic configs spanning thin gas, near-`T_MAX_PHYS` heat (forcing the
   rail-clip term), `k_drag_heat_frac < 1` (forcing the drop term), and
   `c_v != 1`. Committed as `tests/test_p_e3_drag.py`
   (`test_drag_identity_holds_within_lsb_slack`, 6 cases × 3 k_drag values ×
   3 seeds).
3. **A real, latent 128-bit-helper bug was found and fixed on BOTH backends**
   while wiring the oracle counters: `mul128_shr`/`mul128_shr_signed`'s
   hi:lo recombine is undefined behaviour at `shift == 0` (a 64-bit shift by
   64) — the drag oracle is the FIRST caller in the codebase to need
   shift 0. It manifested as silently wrong values **on the GPU only** in
   testing (CPU's `_mul128` path happened not to visibly diverge on the
   tested inputs, but shares the identical UB); fixed by special-casing
   `shift == 0` in both the CPU file-local `mul128_shr` (`eos_solver.cpp`)
   and the device `mul128_shr_signed` (`cuda_fixedpoint_device.cuh`) — see
   §6 for the reproduction and the fix.
4. **Dormancy is exact and measured, not assumed.** Suite failure set is
   byte-for-byte the P-E2b baseline (48 failed / 5 skipped / 1 xfailed,
   name-for-name; +9 passed are this patch's own new tests). Bench digests
   (`tools/bench_two_room.py --ticks 240 --pf1b`) are byte-identical run-to-
   run TWICE post-patch **and** byte-identical against a clean pre-patch
   rebuild of the same command (measured directly, not inferred).
5. **The window battery is clean at `k_drag=0.02`** (damp 0.005, strip 0.5
   restored): all five EOS rails 0, `t_min_gas` never leaves exactly 0.0 the
   whole 4800-tick run. The SAME row is *already* clean without `k_drag` too
   (P-E2a's own prior measurement, reproduced here) — §7 explains what
   `k_drag` adds on top of that baseline.
6. **The design doc's own feel predictions were measured and are WRONG by
   roughly the ticks-per-second factor** — corrected here, not silently
   retuned. Measured free-momentum e-fold at `k_drag=0.02` is **≈49.6 s**
   (design text said "≈2.1 s"); measured door-neck deposit rate at a
   sustained 20 m/s draft is **≈8.05 game-deg/s** (design text said "~96
   game-deg/s"). Both measured values independently reproduce from the
   LOCKED formula by hand (§8) — the implementation matches the spec
   exactly; the design doc's own arithmetic estimate did not include the
   `dt = 1/24 s` factor `kd_q = quantize(k_drag·dt)` requires. **This
   materially changes what k_drag value gives the "~2 s" feel** — flagged
   prominently for Erik's P-E5 sweep.

## 1. What was built (design §2.8, item by item)

### 1.1 The two new dials + EOSSolver's own `c_v`

`[physics.eos]`: `k_drag = 0.0` (per-second rate), `k_drag_heat_frac = 1.0`
(RULING R2). Plumbed config → `EOSSolver::k_drag` / `::k_drag_heat_frac`
(`eos_solver.h`) → `bindings.cpp` `def_readwrite` → `physics_runner.py`'s
`_ep(...)` idiom, exactly like `n_work_ref`.

**`c_v` is a NEW `EOSSolver` member**, not a shared cross-solver reference —
the drag deposit's `ΔT = k_drag_heat_frac·ΔE_cell/c_v` needs no per-cell N
divisor (see §1.3), so it needs only the load-time `c_v` constant, which
`TemperatureSolver` already owns for its own deposits. `EOSSolver::c_v` is
EOSSolver's own copy, bound from the SAME `[physics.thermal] c_v` config key
`physics_runner.py` already reads for `self.temperature.c_v` — one config
key, two solver-local copies (the `n_floor_heat`/`T_MAX_PHYS` precedent).

### 1.2 The forbidden-band load-warn tripwire (task item D)

`physics_runner.py`, right after the EOS dial block: if `[materials.air]
wave_absorb` sits in the open interval `(0, 0.02)` **and**
`[physics.fire] k_wind_strip > 0`, `warnings.warn(..., RuntimeWarning)`
naming the storm audit's §5 window explicitly, with the `k_drag`/
`wave_absorb` equivalence from the design (`A@0.02 ≡ k_drag 0.0067`, audit
§5B) as the suggested fix. Measured (`tripwire_check.py`, ad hoc,
reproducible from any Python session): **fires exactly once** at
`wave_absorb=0.01, k_wind_strip=0.5`; **silent** at shipped defaults
(`wave_absorb=0.0`). `config.toml`'s `[materials.air]` block gained a
matching comment naming the band so a reader hits the warning's context
twice (at the source and at the sink).

### 1.3 The mechanism itself — placement, shrink, deposit

**Placement**: inserted in `EOSSolver::step()`'s step-4 kick loop
(`eos_solver.cpp`), between the existing `|u|` cap block and the
`wind_x[i] = (int32_t)ux;` store — i.e. exactly "after the |u| cap, before
the store," operating on the same `ux`/`uy` wide (`int64_t`) locals the cap
just clamped. Mirrored VERBATIM in `eos_kick_compression_reference` (same
file). Guard: `if (kd_q > 0 && !ts[i])` — `ts` is the same thermal-medium
mask the kick loop's enclosing scope already resolved (`thermal_solid` if
supplied, else `solid`); the `solid`/`is_vacuum`/`ambient-ring` skip was
already applied by the loop's own top-of-body `continue`, so no re-check is
needed here — only the NEW ts exclusion (ruling A1) had to be added.

**The velocity shrink** is the sponge/absorb idiom transcribed verbatim:
`kk_drag = (kd_q < FP_ONE) ? FP_ONE - kd_q : 0`, then a component-wise
magnitude-first `mul128_shr(|u|, kk_drag, 16)` re-signed. This is
load-bearing exactly as the design says: `|u_old|² - |u_new|² ≥ 0`
structurally, because a magnitude-first scale can only shrink |u|
component-wise — no clamp, no signed oracle term needed anywhere downstream.

**`ΔE_cell` needs NO per-cell N divisor** — this is a derivation worth
stating explicitly since it is easy to get wrong by analogy with the
combustion/radiation deposits (which DO divide by N): `u` is a VELOCITY
(intensive), so `ΔE_cell = (|u_old|² - |u_new|²)/2` is already a SPECIFIC
(per-unit-mass) kinetic energy, and `ΔT = ΔE_cell/c_v` is dimensionally
exact without touching N. N enters ONLY in the n-weighted ORACLE counters
(§1.4), which convert the specific quantity to the extensive "N·T" currency
the rest of the arc's energy books use. Getting this wrong (e.g. dividing by
N again, mimicking `deposit_dT_wide_q16`'s 3-factor N-inclusive chain) would
have been a real bug; the design's own "ledger units" phrasing states this
correctly and this as-built makes the derivation explicit for the next
reader.

**The wide divide**: a NEW shared helper `fixedpoint::drag_dT_wide_q16`
(`fixed_point.h`) + device twin `drag_dT_wide_q16_dev`
(`cuda_fixedpoint_device.cuh`), following `deposit_dT_wide_q16`'s exact
pattern (chain the factors as ONE 128-bit product, narrow EXACTLY ONCE, at
the combined shift `FP_SHIFT+RECIP_SHIFT=48`) but NOT reusing it verbatim —
`deposit_dT_wide_q16`'s first factor is `int32_t` (a `deposit` value that
never exceeds Q16.16 range), while `ΔE_cell` here is `int64_t` and can reach
~2^36 (a full stop from the 1000 m/s cap is ~3e10 raw — the exact overflow
class the design's header comment for `deposit_dT_wide_q16` warns about,
generalized to a wider first factor). This is the "follow its pattern"
allowance the brief names, exercised as a genuine adaptation rather than a
literal reuse.

**Applying the deposit**: `dT_intended_wide` (int64, unbounded by q16) is
saturated to `[0, INT32_MAX]` for the `sat_add_q16` call, then the
`t_candidate > t_max_phys_q` ceiling is applied; `dT_applied =
t_candidate - t_old` and `dT_clipped = dT_intended_wide - dT_applied`
capture BOTH the int32-saturation loss and the `T_MAX_PHYS` rail loss in
ONE term by construction (no separate rounding paths to reconcile — this is
why the identity's measured slack is as small as it is, §0.2).
`e_drag_drop_sum` is computed the SAME way with `drop_frac_q = FP_ONE -
heat_frac_q` as the wide-divide's fraction factor, so at the shipped
`k_drag_heat_frac = 1.0` default it is EXACTLY 0 (the fraction factor is
exactly 0, so the wide product is exactly 0 — no rounding involved).

**Phantom-T guard**: `if (n_bulk >= 1) temperature[i] = t_candidate;` — the
guard applies ONLY to the field WRITE. The accounting (`dE_cell_q16`,
`dT_intended_wide`, `dT_applied`, `dT_clipped`, and all four oracle
accumulations) runs unconditionally; at `n_bulk < 1` those n-weighted terms
are automatically ≈0 (the "counted anyway" the design specifies), so no
special-case branch is needed in the oracle itself — only in the store.
Verified directly (`test_phantom_cell_temperature_not_written`, isolated
with a spatially UNIFORM wind field so step 4c's compression work — which
does NOT skip phantom cells — contributes nothing, letting the test see the
drag deposit's own guard cleanly).

**ts skip**: `if (kd_q > 0 && !ts[i])` wraps the WHOLE block — a ts cell
gets neither the velocity shrink nor the deposit. Verified by comparing a
`k_drag=0` run against a `k_drag=1.0` run WITH a `thermal_solid` mask: the
ts cell's velocity and temperature are IDENTICAL between the two runs
(proving drag never touched it), while an ordinary cell's velocity DIFFERS
(proving the mechanism is live and the ts-identity isn't vacuous) —
`test_ts_cells_skip_drag_entirely`.

### 1.4 The oracle — PER-TICK, n-weighted, int64

Four new `EOSSolver` members: `ke_drag_removed`, `e_drag_deposit`,
`e_drag_drop_sum`, `e_drag_rail_clipped` (all `mutable int64_t`,
`def_readonly`). **Reset at `step()` entry — the P-E1 idiom, not P-E2a's
accumulate idiom** (the brief's own question, answered explicitly): the
drag identity is checked ONE TICK AT A TIME, exactly like
`eth_transport_delta`'s ≤0 gate, not diffed against a run total the way
`t_max_phys_hits`/P-E2a's six conduction counters are. The CUDA resident
path's D2H fold (`cuda_eos_resident.cu`) therefore ASSIGNS
(`solver.ke_drag_removed = cnt_host[5]`, not `+=`), matching the sibling
`ecnt` block already using that convention for P-E1's five per-tick
counters; the CUDA per-call chained-dispatch path (`cuda_eos_step.cu`) does
the same.

**Scale**: raw Q16.16² (`dequant = raw / 65536²`), the SAME "N·T" currency
`eth_transport_delta`/`e_floor_sum`/`e_ts_residual` already use.
`ke_drag_removed`'s formula is `mul128_shr(n_bulk, du2_raw, 16)` — a SINGLE
128-bit-safe shift-by-16 of the RAW (un-narrowed) `Δ(|u|²)`, landing
directly on the Q16.16² scale that matches `e_drag_deposit`'s natural
`n_bulk · ΔT_applied` (a direct wide product, no shift). **This is a
deliberate DEPARTURE from the design's inline pseudocode**
(`n·(Δu² >> 16) >> 16`, i.e. two shifts) — worked out from first principles
(§1.3's derivation plus the drag identity's own algebra) rather than taken
literally, because the two-shift reading does not land on the same scale as
`e_drag_deposit` (a dimensional-analysis check the design text's inline
formula does not spell out). The identity holding to 1.48e-7 relative
(§0.2) is the empirical proof this reading is the correct one; see §6 for
the derivation in full and why it also motivated using the codebase's
generic `mul128_shr` 128-bit-safe primitive rather than a raw
`n_bulk * du2_raw` multiply (which CAN overflow int64 in the theoretical
extreme, since `n_total_[i]` is stored as `int32_t` and can in principle
approach its full range).

### 3.7 Gate 8 — feel measurements for the P-E5 brief

**Method**: isolated the drag term directly via `eos_kick_compression_ref`
on a spatially uniform field (zero pressure gradient ⇒ no kick
contribution; zero absorb; uniform ⇒ zero compression work) rather than a
full engine trajectory, so the measurement is the mechanism alone.

**Free-momentum e-fold at `k_drag=0.02`** (a cell at 20 m/s, no driving
force, tracked for 20 s, log-linear fit of `|u|(t)`):

```
measured tau (e-fold) = 49.5996 s
naive continuous-rate prediction (1/k_drag) = 50.0000 s
```

The measured value matches the **continuous-rate** reading `τ = 1/k_drag`
almost exactly (the tiny gap is the discrete-tick vs continuous-time
difference at `dt=1/24`, expected and negligible). **This is NOT the
design doc's stated "≈2.1 s."** `50 / 24 ≈ 2.08 s` — the design's number is
suspiciously close to the measured value divided by the tick rate,
consistent with the design's own back-of-envelope estimate having been
computed as if `k_drag` were directly a per-TICK rate rather than
`kd_q = quantize(k_drag·dt)` (the LOCKED, per-tick-not-per-substep formula
§2.8 itself specifies and this patch implements verbatim). The
implementation was verified against the formula independently (below) —
this is a correction to the design doc's stated feel prediction, not a
defect in the mechanism.

**Door-neck temperature under sustained venting, `k_drag=0.02,
k_drag_heat_frac=1.0`** (a cell held at 20 m/s — re-stamped each tick to
model a pressure-sustained draft the isolated harness cannot itself drive —
tracked for 3 s):

```
T after 1s = 8.053 game-deg   (rate = 8.053 game-deg/s)
T after 3s = 24.159 game-deg
design's stated prediction: ~96 game-deg/s
```

**Hand-derivation, confirming the implementation matches the LOCKED
formula exactly** (not merely close): at `u=20` m/s, `kd ≈ k_drag·dt =
0.02/24 ≈ 8.33e-4`, `u_new ≈ 19.9833`, `Δu² ≈ 0.668` (real, m²/s²),
`ΔE_cell = Δu²/2 ≈ 0.334`, `ΔT_per_tick = ΔE_cell/c_v ≈ 0.334` (c_v=1) →
`0.334 × 24 ticks/s ≈ 8.02 game-deg/s` — matches the measured `8.053`
to within quantization noise. **The design doc's "~96 game-deg/s" is
~12x too high** — again consistent with a missing `dt` factor in the
back-of-envelope estimate (though the exact ratio here is ~12x rather than
the e-fold's ~24x, since the deposit rate's dt-dependence is linear in
`kd` but the velocity DIFFERENCE `Δu²` itself is what is measured per
tick, not compounded the same way — the two "corrections" are not required
to be the same factor, and are reported as independently measured rather
than reconciled to one ratio).

**What this means for P-E5**: at `k_drag=0.02` the interior sink is far
gentler than the design doc implied — real rooms will slosh for **tens of
seconds**, not ~2, and a sustained draft heats a neck cell by **~8
game-deg/s**, not ~96. If Erik wants the "~2 s, ~96 deg/s" FEEL the design
doc originally described, the dial that produces it is **`k_drag ≈ 0.5`**
(giving `τ = 1/0.5 = 2 s`) or higher, roughly 25x the audit's originally
suggested `~0.02-0.05` sizing — a materially different starting point for

## 5. §5 — Deviations from the brief, summarized

1. **A real, latent undefined-behaviour bug in the shared 128-bit
   `mul128_shr`/`mul128_shr_signed` helpers was found and fixed on BOTH
   backends** while wiring the oracle's "no shift" counters
   (`e_drag_deposit`/`e_drag_drop_sum`/`e_drag_rail_clipped`).
   **Reproduction**: both helpers' own doc comments state their valid
   domain as `0 < S < 64`; nothing in the codebase before this patch ever
   called them with `S=0` (every existing call site uses 16/32/48). The
   hi:lo recombine `hi << (64 - S)` is undefined behaviour at `S=0` (a
   64-bit shift by 64). On the GPU this manifested as **visibly, reliably
   wrong values** in `cuda_kick_check.py`'s PART 1 drag-forcer config —
   `e_drag_deposit`/`e_drag_drop_sum`/`e_drag_rail_clipped` all came back
   `-576` (`= -(24×24 grid cell count)`, i.e. `-1` accumulated once per
   cell — consistent with the shift-by-64 degenerating to a no-op shift on
   this hardware's mod-64 masking, corrupting every per-cell contribution
   identically) while `ke_drag_removed` (computed at `S=16`, unaffected)
   matched the CPU reference exactly. The CPU `_mul128` path shares the
   IDENTICAL UB expression but did not visibly diverge on any tested input
   (an identity-slack script run BEFORE the fix already showed the correct
   answer on CPU, to 1.48e-7 relative) — plausibly because MSVC's codegen
   for a compile-time-constant shift amount of 0 behaves differently than
   nvcc's for the same source, but this was not chased further since the
   FIX (special-case `S==0` to return the product's low 64 bits directly,
   no `hi` contribution) removes the UB on both sides regardless of which
   one "happened" to work. **Fixed as a purely additive extension** of
   each helper's valid domain (no existing `S∈(0,64)` caller's behaviour
   changes) — the same "report, don't hide" precedent P-E2b set for its own
   overflow-bug discovery. Verified: PART 1 of `cuda_kick_check.py` flipped
   from a GPU-only counter mismatch to bit-identical on all 40 configs
   after the fix.
2. **The design's inline oracle formula for `ke_drag_removed`
   (`n·(Δu² >> 16) >> 16`, i.e. two shifts) was NOT taken literally** — a
   dimensional-analysis derivation (§1.4) showed the two-shift reading
   lands `ke_drag_removed` on a DIFFERENT scale than `e_drag_deposit`'s
   natural `n·ΔT` (no shift), which would make the drag identity
   (`ke_removed == 2c_v·Σ`) fail by a factor of ~65536. The implemented
   formula (`mul128_shr(n_bulk, du2_raw, 16)`, a SINGLE shift applied to
   the raw product) is the one that reproduces the identity to 1.48e-7
   relative — treated as the authoritative resolution of an ambiguous
   inline pseudocode fragment, verified empirically rather than argued.
3. **The design's own feel predictions in §2.8 ("Free-momentum e-fold
   ≈2.1 s"; "~96 game-deg/s" into neck cells) do not match the measured
   values** (§3.7: measured ≈49.6 s and ≈8.05 game-deg/s respectively, both
   independently reproduced by hand from the LOCKED formula) — reported as
   a correction to the design doc's stated numbers, not a defect in the
   implementation (the implementation matches the formula exactly; the
   design's arithmetic estimate appears to have omitted the `dt=1/24 s`
   tick-rate factor). Flagged prominently because it changes what `k_drag`
   value gives the feel Erik was expecting when he wrote the design.
4. **Baseline was not captured strictly before any edit landed** — the
   author began implementing before running the pristine baseline suite,
   then recovered an exact clean baseline via `git stash` (reverting all
   tracked changes, rebuilding CPU, running the suite, then restoring the
   patch) rather than losing the comparison. The recovered baseline
   (48 failed / 2173 passed / 5 skipped / 1 xfailed) matches the P-E2b
   as-built's own stated numbers exactly, so the comparison in §3.2/§3.6 is
   exact despite the ordering slip. Reported per the workflow's "report,
   don't hide" norm.
5. **`counters_out` grew 5 → 9 slots, not "~8" as the brief's own estimate
   said** — four new counters (`ke_drag_removed`, `e_drag_deposit`,
   `e_drag_drop_sum`, `e_drag_rail_clipped`), all four named explicitly in
   design §2.8's own oracle section, so this is the literal count the
   design specifies; the brief's "~8" was an approximation, noted rather
   than treated as a target to hit.
6. **Two of the four new committed tests needed a redesign mid-writing**:
   the first version of `test_phantom_cell_temperature_not_written` and
   `test_ts_cells_skip_drag_entirely` used per-cell RANDOM wind fields
   (via the shared `_make_case` helper) and failed — not because the
   mechanism was wrong, but because `eos_kick_compression_ref` runs BOTH
   step 4 (kick+drag) AND step 4c (compression work) in one call, and
   step 4c's `div(u_new)` term does NOT skip phantom/ts cells, so a
   non-uniform wind field lets compression work write T at exactly the
   cells the drag guard is supposed to leave alone — corrupting the
   isolation. Fixed by rebuilding both tests on a SPATIALLY UNIFORM wind
   field (`div == 0` everywhere ⇒ step 4c is a structural no-op), which
   cleanly isolates the drag deposit as the only possible T-write source.
   Caught before committing; reported because the next reader touching
   this reference function should know it exercises BOTH steps, not just
   the one being tested.
