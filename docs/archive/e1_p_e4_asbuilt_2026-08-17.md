## 2. §2.4 trust gate — what was built

New shared helper `fixedpoint::work_fade_clamp01_q` (`cpp/src/fixed_point.h`),
FP_HD (host + device, pure int64 — no 128-bit product, so it needs no `_dev`
twin):

```cpp
FP_HD inline q16 work_fade_clamp01_q(q16 ratio_q) {
    int64_t f = ((int64_t)ratio_q << 1) - (int64_t)FP_ONE;
    if (f < 0) f = 0;
    else if (f > (int64_t)FP_ONE) f = (int64_t)FP_ONE;
    return (q16)f;
}
```

`ratio_q` = n/n_work_ref in Q16.16, computed by the CALLER via `recip_mul`
(host) / `recip_mul_dev` (device) against a per-tick fold
`recip_n_work_ref = make_recip(max(n_work_ref, 1e-6))` — the SAME
per-tick-not-per-cell idiom `recip_cv` (P-E3) already uses. `n` is the
EXISTING `n_total_` (live step) / local `n_total` (CPU reference twin) /
`d_ntot` (CUDA — the same plane K1's kick already reads) bulk-N plane — zero
new reductions, no new synced state, matching the design's explicit
instruction.

Applied in all three step-4c twins, identically, BEFORE the ±T_WORK_CLAMP
compare:

```cpp
q16 k = mul_q16(gamma_m1_q, div_new);
k = mul_q16(k, dt_q);
{
    const q16 ratio = recip_mul(n_total_[i], recip_n_work_ref);   // recip_mul_dev on device
    const q16 fade = fixedpoint::work_fade_clamp01_q(ratio);
    k = scale_mag(k, fade);   // magnitude-first: negative k fades TOWARD 0
}
```

`scale_mag` (the existing sponge/outflow-limiter shared helper) is reused
verbatim rather than hand-rolling a new magnitude-first shrink — it is
EXACTLY the "magnitude-first idiom" the design cites, already extracted as a
shared primitive since before this arc.

## 3. §2.7 reversible work — what was built

**Single-compare clamp form (pinned).** Where the old code had an exclusive
`if (k > work_clamp_q) ... else if (k < -work_clamp_q) ...` pair, the new
code computes the magnitude once and clamps that:

```cpp
const bool k_neg = (k < 0);
q16 w = k_neg ? (q16)(-(int64_t)k) : k;
if (w > work_clamp_q) { w = work_clamp_q; ++work_clamp_hits; }
```

This is bit-for-bit equivalent in hit-count semantics to the old pair
(`|k| > clamp` ⟺ `k > clamp OR k < -clamp`), and it is what makes `w`
available for both branches below without recomputing it.

**Compression (`k_neg == true`) — KEPT VERBATIM**, per the design's explicit
instruction not to reimplement it as a multiply-by-`(1+w)`:

```cpp
const q16 k_signed = (q16)(-(int64_t)w);
const q16 dT = mul_q16(k_signed, temperature[i]);
t_new = sat_add_q16(temperature[i], (q16)(-(int64_t)dT));
```

**Expansion (`k_neg == false`, including the pinned `k==0` identity) — the
inverse via the SHARED `floordiv_q` helper** (`fixed_point.h`, already
created by P-E1 for the recovery divide — not re-derived):

```cpp
t_new = (q16)floordiv_q((int64_t)temperature[i] << 16,
                        (int64_t)FP_ONE + (int64_t)w);
```

Identical in all three twins: `eos_solver.cpp`'s live `step()` (the 4c
loop, currently at lines ~877–924 post-patch), `eos_kick_compression_reference`
(same file, ~line 1706–1730), and `cuda_kick_compression.cu`'s
`compression_kernel` (K2) — the device version calls `recip_mul_dev` in place
of `recip_mul` for the fade ratio and is otherwise a verbatim transcription
(same `floordiv_q`/`scale_mag`/`mul_q16`/`sat_add_q16` shared FP_HD helpers,
which compile identically on host and device).

**ABI surface touched** (as `n_work_ref` needed threading through, the SAME
class of change P-E3's `k_drag`/`k_drag_heat_frac`/`c_v` triggered):
`eos_kick_compression_reference` and `breach_cuda::eos_kick_compression`
both gain a `float n_work_ref` parameter (`counters_out` size UNCHANGED at
9 — no new counter, only existing ones' values shift); `KickScalarFolds`
gains `int64_t recip_n_work_ref`; `kick_scalar_folds()` gains the
`n_work_ref` parameter; `compression_kernel` (K2) gains `n_total` and
`recip_n_work_ref` parameters (K2 did not read the N plane before —
`kick_compression_launch_resident` already threads `d_ntot` through for K1,
so no new device pointer plumbing was needed at the resident-scratch level,
only a new argument on the K2 launch); the `eos_kick_compression_ref` /
`cuda_eos_kick_compression` pybind entries both gain
`py::arg("n_work_ref") = 0.25f`.

## 4. Item C — the inherited P6.4 gate repair

**Root cause** (verified independently, matching P-E2a's own revert+rebuild
finding at as-built §8.3): `test_cuda_p64_kick_compression` PART 2 tried to
reconstruct the true step-4-entry state by replaying the advection substeps
(`eos_sl_advect_ref`) on a tick-start snapshot, then comparing the replay's
digest against `EOSSolver.digest_advect`. P-E1 made `eos_sl_advect_reference`
u-only (temperature is a read-only src slot now, its `.t` slot discarded)
and moved `digest_advect` to hash `(wx, wy, T-AFTER-RECOVERY)` — a 3-field
chain versus the replay's 2-field chain. These are **structurally
incomparable digests**, not merely stale values; the comparison could never
pass regardless of whether the underlying wind/T state agreed.

**The deeper finding** (this as-built's own contribution, verified by
instrumented reproduction before touching the test): the field-level
ground-truth check (`f_ref["temperature"] == g.temperature`) was ALSO
broken, for a related but distinct reason — `t0` (the snapshot fed into the
isolated tail) is captured at TICK START and is never advanced by anything
any more (T evolution moved entirely into the P-E1 energy-transport pass,
which has no isolated Python entry point at this granularity), so by tick 1
it is missing that tick's own transport delta. Reproduced directly on the
pre-repair code: the digest-pair printout showed `digest_velocity` matching
the real solver **exactly** while only `digest_compression` diverged — proof
that step 4 (the kick) is completely unaffected, because it reads
pressure/N/absorb and **never reads temperature**; only step 4c (compression
work) consumes the now-stale T.

**The repair** (`tests/cuda_kick_check.py`, `part2_trajectory`): the
`digest_advect` comparison is DELETED (not worked around — there is no
value it could meaningfully be compared to). The wind-side reconstruction
is KEPT (still valid, unaffected by the T retirement) and its ground-truth
comparison is NARROWED to exactly what remains true:
- `res_ref[0]` (`digest_velocity`) **==** `eos.digest_velocity` — kept.
- `wind_x`/`wind_y` fields **==** the engine's post-tick bytes — kept.
- the T-INDEPENDENT rail counters (`u_clamp`, `u_max`, `work_clamp` — the
  SS2.4 fade and the ±T_WORK_CLAMP compare both key off N/divergence, never
  T) **==** the solver's cumulative deltas — kept, newly split out from the
  old blanket 5-counter check.
- `digest_compression`, the `temperature` field, and the T-dependent rail
  counters (`energy_floor`, `t_max_phys`) are **no longer checked against
  the real solver** — that coverage was never lost, it lives at its
  rightful owner, P-E1's own `cuda_bulk_flux_check` PART 3, which already
  proves the energy-transport pass producing the TRUE step-4-entry T is
  bit-identical CPU↔GPU and closes the energy books every tick.
- The full CPU-ref-vs-GPU comparison (`_compare(...)`, covering BOTH digests,
  ALL fields, ALL 9 rail counters) is **UNCHANGED** — this is the actual
  core P6.4 proof, and it needed no repair: CPU ref and GPU are fed the
  identical (possibly-stale-T) input, so they must agree with each other
  regardless of whether that input matches the real engine.

**What the repaired gate now asserts, precisely**: PART 2 proves (a) the
wind-reconstruction pipeline (advection replay → kick) remains bit-exact
against the real engine over a 120-tick realistic trajectory, post-P-E1's
retirement of the T-write, and (b) the isolated kick+compression tail is
bit-identical CPU↔GPU on every field, every digest, and every rail counter,
over that same 120-tick trajectory of REALISTIC (not just PART 1's synthetic)
states. It no longer claims — and never again should be read as claiming —
that the isolated tail reproduces the real engine's post-tick TEMPERATURE.

**Measured after repair**: PART 1 and PART 2 both green (PART 1: 40/40
configs bit-identical, all rail engagements non-vacuous; PART 2: 120 ticks,
wind ground truth held, CPU ref == GPU on everything, peak |u| 1008.4 m/s,

## 6. Gate 4 — the §2.7 direct unit oracle

Committed: `tests/test_p_e4_reversible_work.py`. Drives
`eos_kick_compression_ref` (the REAL step-4c loop, not a re-derived Python
mirror) on a 5×5 probe grid, single center cell, uniform pressure (so the
kick's pressure gradient is exactly zero and step 4 is a no-op on wind —
step 4c reads back EXACTLY the wind field the test sets), ambient gas
density (n_bulk≈1.0, far above `n_work_ref`'s trust band so the SS2.4 fade
stays ≈1 and does not confound this measurement), `k_drag=0` (dormant),
divergence engineered via the probe cell's east/west wind neighbours.

### 6.1 AT the clamp — the rigorous bound

**Why AT the clamp is exact and BELOW it is not**: at the clamp, the
pre-clamp `|k|` is driven far past ±T_WORK_CLAMP in both directions, so `w`
is bit-identical in both legs of a cycle REGARDLESS of any upstream
rounding noise in the divergence pipeline. Derived algebraically (see the
test module's docstring for the full derivation): writing
`T1_int = ceil(real T1)` (compression rounds its increment UP — `mul_q16`
floors a negative product) and `T2_int = floor(real T2)` (the
floor-toward-`-inf` expansion), compress-then-expand recovers T0 EXACTLY and
expand-then-compress loses AT MOST 1 raw count, one-way, for ANY T0 sign.

Measured (v=300 m/s, pre-clamp |k|≈15 ≫ 0.5, both legs confirmed to engage
`work_clamp_hits`):

| order | T=positive (300) | T=sub-ambient (−100) |
|---|---:|---:|
| compress-then-expand | **residual = 0** | **residual = 0** |
| expand-then-compress | **residual = 0** | **residual = 0** |

Both within the design's predicted bound (0 exact; ≤1 LSB one-way). The
expand-then-compress residual happened to land on 0 rather than −1 for
these particular T0 values — the bound is `∈ {0, −1}`, not a guarantee of
exactly −1; asserted as `residual in (0, -1)`, both pass.

### 6.2 Below the clamp — measured (not a tight pin)

Below the clamp, the two legs' `|k|` agree only up to the DIVERGENCE
PIPELINE's own truncation noise (`mul_q16` rounds a negative product toward
`-inf`, not symmetrically with its negation on the SAME magnitude) — a
mismatch of order 1 raw q16 COUNT IN `w`, unrelated to §2.7's own
floor/mul_q16 story, that gets amplified by T0 itself (residual ≈
T0 · Δw). Measured at T0=300, v=2 m/s (k≈0.1):

| order | T=positive | T=sub-ambient |
|---|---:|---:|
| compress-then-expand | +272 raw (0.14% of T0) | −182 raw |
| expand-then-compress | +273 raw | −182 raw |

Reported and pinned with a loose relative bound (~0.5% of \|T0_raw\|, floor 8
counts) — generous enough to absorb the pipeline noise, tight enough that a
genuinely broken mechanism (which would show an O(w) ~10%+ error) would
still fail it.

### 6.3 The asymmetric-cycle figure

One compression at w≈0.4 (v=8 m/s) against two expansions at w≈0.2 each
(v=4 m/s), T0=300:

| | measured (NEW law) | analytic (NEW law) | analytic (OLD law, retired) |
|---|---:|---:|---:|
| per-cycle loss | **2.776%** | 2.778% | 10.400% |

Matches the design's worked example (~2.8% new vs ~10.4% old) to within
0.002 percentage points on the new-law side (the tiny gap is Q16.16
quantization of the achieved w's away from the nominal 0.4/0.2). Asserted:
measured loss within 1pp of the analytic new-law prediction, and clearly
below the old law's figure (by >3pp margin).

## 14. Deviations from the brief, summarized

1. **Baseline was not captured strictly before the first edit** (the same
   ordering slip P-E3's as-built reported). Recovered via `git stash push
   -u` back to the parent commit (`a022060`), a clean CPU+CUDA rebuild, a
   fresh suite run, then `git stash pop` and rebuild forward — exact,
   name-sorted, programmatically diffed against the patched tree's own
   fresh run, matching the brief's stated expectation
   (48/2182/5/1) precisely. Reported per the workflow's "report, don't
   hide" norm.
2. **One test flipped green that the brief did not predict or ask for**:
   `test_air_boundary::test_ambient_gate3_udamp_band_absorbs_reflection`
   (§7). Not retuned, not touched — a measured consequence of the law
   change moving the acoustic field's baseline reflection back up from
   P-E1's collapsed noise floor. Reported prominently rather than silently
   accepted as a free win.
3. **The P6.4 gate repair (item C) went one layer deeper than the brief's
   framing implied.** The brief attributed PART 2's divergence entirely to
   the `digest_advect` comparison. That comparison IS structurally broken
   (§4), but repairing only it would have left a SECOND, related breakage
   in place (the field/counter ground-truth checks against a T that is
   provably stale from tick 1 onward) undiagnosed. Root-caused via
   instrumented reproduction (the digest-pair printout showing
   `digest_velocity` matching while only `digest_compression` diverged)
   before writing the repair, and the repair addresses both findings
   together as one coherent new contract rather than patching the narrower
   symptom.
4. **`n_work_ref` is threaded as a genuinely new parameter through six
   function signatures** (`eos_kick_compression_reference`,
   `breach_cuda::eos_kick_compression`, `kick_scalar_folds`,
   `compression_kernel`, plus the two pybind entries) rather than being
   read as a config-file value inside the kernel — the same ABI-growth
   class P-E3's `k_drag`/`k_drag_heat_frac`/`c_v` triggered, and reported
   here for the same reason: a future reader hunting for every call site
   that needed updating should find this list rather than re-derive it.
5. **The design's literal pseudocode `clamp01_q(recip_mul(n, recip_n_ref))`
   was not implemented as a single opaque call** — it is expanded into
   `recip_mul` (the ratio) then `work_fade_clamp01_q` (the shape), because
   the shaping math (`2·ratio − 1`, clamped) needs an int64 widening step
   the design's one-line phrasing does not spell out (a dense pocket at
   ratio ≫1 — P-E0 measured the cold-rail window at 7–37× the trust band —
   would overflow a naive q16 `2×` without it). The two-step form is also
   what lets one tiny shared helper (`work_fade_clamp01_q`, pure int64, no
   128-bit product) serve BOTH backends, with only the ratio computation
   itself needing a `recip_mul`/`recip_mul_dev` backend split — mirroring
   the `deposit_dT_wide_q16`/`_dev` and `drag_dT_wide_q16`/`_dev` split
   precedent from P-E2b/P-E3.
