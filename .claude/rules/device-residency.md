# Device residency: the resident tick, the CUDA build, the twin ledger

Fires on contact with these files. CLAUDE.md's index says what each system is
and who must use it; this file holds the constraints the code cannot say. New
C++ sim TUs go on the `/fp:strict` list in `cpp/CMakeLists.txt`, always.

## Stamp kernel
- The resident tick builds slot 6's five planes ON THE DEVICE from the unit rows the host's C++ stamp flattened; the five planes are NEVER in the entry `from_host` on a tick the rows served.
- The CPU stamp stays THE oracle (gameplay reads its planes) and the law is its: reset, then MAXes, the permeability a WRITE (the LAST row wins where bodies overlap, not a running min).
- `take_stamp_rows` returns None, and the tick uploads the host's planes instead, when no C++ stamp ran or a tile changed between the stamp and the tick. In a batch one env's None makes every env upload its planes that tick.
- A new stamp output is a column of the rows, the kernel and the CPU stamp in ONE change, gated by `tests/cuda_stamp_check.py` and every `cuda_s8a_check` leg.
- DEBT: the refill (`_neighbor_mean`, atmosphere) is still host Python in both stamp paths.

## Batched resident engine
- Slot 7 of N HOMOGENEOUS envs (one grid shape, gas table, tilt, config; space maps; no light until #81) in ONE device chain.
- Every launch core is `(N, h, w)`: `blockIdx.y` is the env, pointers rebased per env (`bptr`), the kernel body verbatim, NEVER a tall grid. Per-env scalars are `(N,)` columns; scratch is keyed `(N, h, w)`; no allocation in a steady-state tick.
- The EOS pre-stage is the device's: a fold table built once per config and range-checked (a refused row is the env's failure flag). Substep loops run to the batch's max n_sub; an env past its own is masked (`sub_off`).
- Every book lands per env in ONE arena and folds into `engs[e]` at the tail's ONE D2H, assign vs accumulate as on the CPU.
- ONE blocking tick stream (`tstream`) for every launch, copy and memset; the tick's only host syncs are `tick_sync_point("max_n_sub")` and `("books")`.
- The played `--cuda --resident` tick is `run_resident_batch` at N = 1: one code path, never a second N = 1 copy. A `ResidentBatch` runs each env's host slots through `Simulation._step_pre_physics` / `_step_post_physics`.
- A new resident core is born `(N, h, w)` on `tstream`, masked inside a substep loop, its books a region of the arena; gated by `cuda_s8a_check` (N = 1 == CPU, tol 0), `cuda_batch_invariance_check` (env i of N == env i alone), `cuda_prestage_parity_check` and `cuda_tick_capture_check` (the chain captures, the two syncs named).
- ACCEPTED GAPS: the sky bracket (ambient, N = 1 only); the books come down every tick while host gameplay is in the loop; the resident path writes no `dbg_T_pre_advect`.

## The device-taken blast source
- `run_resident_batch(..., div_source_dev=)` (and `ResidentBatch.step(take_sources=)`) hands slot 7 the blast source the applier's SOURCES stage took ON THE CARD: the EOS stage then copies it device to device and does not read the engines' `eos.div_source`. The played tick passes none and uploads as before: a change there is a Class-P change (`.cuda_green` at HEAD), held by every `cuda_s8a_check` leg and `tests/cuda_unit_payloads_check.py`'s HANDOVER (device-taken == uploaded, every tick).

## Build id
- Generated at BUILD time on every build, never at configure; the TU is rewritten only when the id changes; in the CPU and the CUDA module alike. `require_snapshot` and `tools/cuda_green.py` compare it with HEAD.
- `match_replay.build_id()` stays THE describe helper: never a second.

## Class P / Class T + the twin ledger
- Every device twin is a row of `tests/twin_manifest.toml`: class P (the played `--cuda` / `--resident` game runs it: level PER PATCH, never in debt) or T (training only: carries debt, refused at the training doors). Its `files` are GENERATED by `tools/twin_manifest_gen.py`, never hand-edited; stale = `tests/test_twin_debt.py` red: regenerate and commit.
- Debt is COMPUTED (`tools/twin_debt.py`). A `src/simulation/` module the corpus runs is in a twin's files or a `[not_twinned]` row with its reason. A twin's traced files are what the corpus RAN under its slot, so a law the corpus never exercises is not traced.
- A branch whose diff from main touches a Class-P twin's files or device sources, or a `[class_p] build` path, merges only with `.cuda_green` == HEAD, written by a green `tools/cuda_green.py` run on this checkout's own CUDA build AT HEAD (`tests/test_class_p_level.py` never skips; the git-workflow merge step refuses on it). Such a patch moves its twins' `level_at` in its last commit (`tools/twin_debt.py --mark-level`).
- A Class-T twin's debt never blocks a merge; it blocks the device training door (`require_snapshot(tag, "device")` refuses while the ledger is non-empty). It may share a `src/` file with a Class-P twin, whose stamp a change there still needs. A change to its law's files lands with its kernel, or leaves it in debt until its catch-up.
